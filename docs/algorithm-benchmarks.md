# 本地算法基准测试记录

> 阶段：**Algorithm Engine V1 / P0**
> 脚本：`packages/editor-core/src/algorithms.bench.ts`（配置 `vitest.bench.config.mts`）
> 复现命令：`pnpm bench`（等价于 `pnpm --filter @acs/editor-core bench`）

本文件只记录**真实执行**得到的数据，不包含估算值。每次修改算法核心时应重新运行并把结果追加为新的记录小节。

## 1. 测量协议

- **预热 + 采样**：每个场景先执行 1 次预热（不计入），再按固定采样次数重复，取总耗时与单次均值。
- **批量操作**：`batchSize` 表示「一次采样内重复执行的操作数」，单次耗时 = 总耗时 / (采样次数 × 批量)。
- **最快/最慢**：按单次采样耗时记录，用于观察抖动（GC、JIT 去优化）。
- **确定性素材**：所有输入由 `fixtures.ts` 生成，同一 `seed` 结果一致，保证可对比。
- **计时器**：`performance.now()`；`measure` 自身不申请 DOM、不写磁盘。

采样规模约定：小尺寸（≤512）取 30 次采样；大尺寸（≥1024）取 3 次采样；纯逻辑场景取 300 次采样 × 批量。

## 5. 内存峰值（真实测量）

用 `process.memoryUsage()` 前后对比，连续创建 4 张 4096×4096 RGBA 位图（每张 4096×4096×4 = 64 MB，理论合计 256 MB）：

| 指标 | 变化 |
| --- | --- |
| `arrayBuffers` | **+247.9 MB** |
| `rss` | **+248.0 MB** |
| `heapUsed` | −11.5 MB（GC 抖动，不代表真实下降） |

结论：像素数据几乎全部驻留在 ArrayBuffer 中，实际增量与理论值一致（约 1:1）。因此：**算法实现中绝不能同时保留多份全尺寸位图副本**；预览与成品应按分辨率分级，及时释放中间缓冲。

## 6. 本次定位到的真实性能缺陷

首次基准运行时发现 **`hashRaster` 在 4.19MP 上耗时 2610 ms**（约 620 ns/像素）。根因：初版实现逐字节做 `BigInt` 运算（`0xcbf29ce484222325n` 的 FNV-1a 64 位），每次迭代产生 BigInt 分配与装箱。

修复：改为**两路 32 位哈希**（FNV-1a 32 位 + 二次混合），全部使用 `Math.imul` 整数运算，输出 16 位十六进制指纹，保留「同输入同输出」的稳定性。

| 版本 | 2048×2048 单次耗时 | 1024×1024 单次耗时 |
| --- | ---: | ---: |
| 修复前（BigInt FNV-1a 64） | 2610 ms | 约 640 ms |
| 修复后（双路 32 位） | **61.8 ms** | **8.2 ms** |

约 **42×** 提速，且 `fixtures.test.ts` 中的稳定性与区分度断言全部通过。这是 P0 交付的第一个真实算法性能问题。

## 7. 对 P1/P2 设计的直接影响

1. **预览必须降分辨率**：1MP 单遍像素运算 10–40ms、4MP 47–176ms。交互预览应控制在 ≤512²（<10ms），高清结果延迟渲染，禁止每次鼠标移动全分辨率重算。
2. **禁止在交互路径做 PNG 编解码**：4MP 编码 127ms、解码 236ms；画布与位图之间应直接传递 `RasterImage`，编码只在导出/落盘时发生。
3. **结果指纹可用于缓存**：`hashRaster` 1MP 8.2ms 足够作为「相同输入 + 相同参数」的缓存键，配合参数指纹实现复用。
4. **内存纪律**：单张 4K RGBA 占 64MB，多副本会迅速逼近移动端上限；实现时必须原位写入或分块处理。
5. **接缝/颜色算子的成本上限**：颜色变体类算子接近 `noise`（4MP ≈ 176ms），属于必须走预览分级 + 异步的范畴。

## 9. P1 图案引擎测量（2026-10-19，同一台机器）

输入固定：512×512 棋盘格图案，参数 `columns=4, rows=4, motifScale=0.5, rotationDeg=8, gapX=6, gapY=6`（成品约 1042×1042 ≈ 1.09MP）。

### 9.1 优化后结果

| 场景 | 规模 | 单次耗时 |
| --- | ---: | ---: |
| `buildPattern` 成品（final） | 1.09MP，16 个单元 | **91–148 ms** |
| `buildPattern` 预览（previewMaxEdge 512） | ≤512 边长 | **47–52 ms** |
| `buildPattern` 预览（previewMaxEdge 256） | ≤256 边长 | **27–33 ms** |
| `repeatTile` 2×2（源 512） | 1024×1024 | **1.3–3.8 ms** |
| `mirrorTile` 2×2（源 512，both） | 1024×1024 | **12–17 ms** |
| `adjustColor`（饱和度+对比度） | 512×512 | **5–6 ms** |
| `measureSeams`（双轴） | 512×512 | **0.17–0.22 ms** |
| `makeSeamless`（both, medium） | 512×512 | **4.6–5.4 ms** |
| `hashRaster`（对照） | 1024×1024 | **6.3–11.5 ms** |

### 9.2 由测量驱动的优化（真实缺陷，非猜测）

首版实现逐像素调用带坐标校验的 `rasterIndex()`，测得：

| 场景 | 优化前 | 优化后 | 倍数 |
| --- | ---: | ---: | ---: |
| `repeatTile` 1024×1024 | 82.5 ms | 1.3–3.8 ms | **约 22–63×** |
| `mirrorTile` 1024×1024 | 86.0 ms | 12–17 ms | **约 5–7×** |
| `buildPattern` 成品 | 417 ms | 91–148 ms | **约 3–4.5×** |
| `buildPattern` 预览 512 | 170 ms | 47–52 ms | **约 3.3×** |

变更点：
1. `repeatTile`/`mirrorTile` 改为整行 `Uint8ClampedArray.set`（非镜像行是内存拷贝级），镜像行用直接索引反序复制，去掉逐像素校验。
2. `renderLayout` 增加不透明快路径（`alpha === 255` 直接写入）与全透明跳过，并整行拷贝不透明区域。
3. `resizeRaster` 缩小路径的热循环改为直接索引算术（去掉逐像素 `rasterIndex`）。

### 9.3 结论（对 P3 集成的硬性要求）

1. **预览必须小且必须节流**：256 预览单次 27–33ms，已超过 16ms 帧预算；因此只允许在**参数变化**时重建，禁止跟随鼠标移动/画布平移重建。
2. **接缝检查非常便宜**（0.17ms），UI 可以实时显示接缝度量数值。
3. **成品 1MP 约 0.1s、4MP 会到数百毫秒**，必须异步 + 运行状态 + 可取消（P3）。
4. 预览的固定开销主要来自对**整幅源图**做面积平均缩小（该项不随预览尺寸缩小而线性下降）；P3 应缓存一份小尺寸 mip 复用。

### 9.4 测量口径与不确定性

- 本机为笔记本（i5-11260H），非受控基准环境；**同一天不同次运行差异可达 ±40% 甚至更高**（见 `hashRaster` 1MP 在 6.3–11.5ms 之间波动）。
- 因此上表一律给出**区间**而不是单值；任何「节省 X%」的说法都必须附带区间与复现命令。
- 复现：`pnpm bench`（约 20 秒，输出 CSV 行 `BENCH|...` 便于机器比对）。

## 10. P2 图像处理测量（2026-10-19，同一台机器）

输入固定：512×512 对角渐变（`fillGradient`）。

| 操作 | 参数 | 单次耗时 |
| --- | --- | ---: |
| `applyOpacity` | opacity 0.5 | 4.7–5.5 ms |
| `cleanAlphaFringe` | threshold 16 | 5.9–8.0 ms |
| `analyzeTransparentEdges` | threshold 16 | 6.1–7.5 ms |
| `sharpen` | amount 60, radius 1 | 77–81 ms |
| `denoise` | strength 60, 3×3 中值 | 79–230 ms |
| `inspectOutput + buildOutputReport` | 254mm @ 300dpi） | 0.002 ms |

### 10.1 由测量定位并修复的性能缺陷

`denoise` 首版在**每个像素上**执行 `samples.slice(0, count).sort()`，512×512 实测 **896ms**（每次调用产生约 26 万次数组分配）。

修复：
1. 边界改为**复制边缘**采样，任意位置固定 9 个样本（不再按边界裁剪样本数）。
2. 复用同一个 9 元素数组，用**插入排序**求中值，零每像素分配。
3. 预计算 9 个邻域字节偏移，去掉内层 `Math.min/Math.max`。

结果：**896ms → 79ms（约 11×）**，`denoise` 的中值与强度混合测试全部保持通过。

> `denoise` 的 79–230ms 区间跨度较大（该场景只取 3 个采样且排在基准末尾，受前面重负载影响）；**保守应按 230ms 级别对待**。

### 10.2 结论（对 P3 集成的硬性要求）

1. `sharpen` / `denoise` 是**重操作**（0.26MP 约 0.08s，4MP 预计数秒）：只允许在成品阶段异步执行 + 显示运行状态 + 可取消，**禁止进入拖拽/预览路径**。
2. `applyOpacity`、`cleanAlphaFringe`、`analyzeTransparentEdges`、`inspectOutput` 足够轻量，可用于实时反馈（接缝/有效 DPI 提示等）。
3. 所有图像处理输出都应通过 `contentHash`（`hashRaster`）记录，用于缓存命中与「结果是否真的变化」的判断。
