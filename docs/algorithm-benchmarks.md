# 本地算法基准测试记录

> 阶段：**Algorithm Engine V1 / P0**
> 脚本：`packages/editor-core/src/algorithms.bench.ts`（配置 `vitest.bench.config.mts`）
> 复现命令：`pnpm bench`（等价于 `pnpm --filter @acs/editor-core bench`）

本文件只记录**真实执行**得到的数据，不包含估算值。每次修改算法核心时应重新运行并把结果追加为新的记录小节。

## 1. 测量协议

- **预热 + 采样**：每个场景先执行 1 次预热（不计入），再按固定采样次数重复，取总耗时与单次均值。
- **批量操作**：`batchSize` 表示「一次采样内重复执行的操作数」，单次耗时 = 总耗时 / (采样次数 × 批量)。
- **最快/最慢**：按单次采样耗时记录，用于观察抖动（GC、JIT 去优化）。
- **确定性素材**：所有输入由 `fixtures.ts` 生成，同一 `seed` 结果一致，保证可对比。
- **计时器**：`performance.now()`；`measure` 自身不申请 DOM、不写磁盘。

采样规模约定：小尺寸（≤512）取 30 次采样；大尺寸（≥1024）取 3 次采样；纯逻辑场景取 300 次采样 × 批量。

## 5. 内存峰值（真实测量）

用 `process.memoryUsage()` 前后对比，连续创建 4 张 4096×4096 RGBA 位图（每张 4096×4096×4 = 64 MB，理论合计 256 MB）：

| 指标 | 变化 |
| --- | --- |
| `arrayBuffers` | **+247.9 MB** |
| `rss` | **+248.0 MB** |
| `heapUsed` | −11.5 MB（GC 抖动，不代表真实下降） |

结论：像素数据几乎全部驻留在 ArrayBuffer 中，实际增量与理论值一致（约 1:1）。因此：**算法实现中绝不能同时保留多份全尺寸位图副本**；预览与成品应按分辨率分级，及时释放中间缓冲。

## 6. 本次定位到的真实性能缺陷

首次基准运行时发现 **`hashRaster` 在 4.19MP 上耗时 2610 ms**（约 620 ns/像素）。根因：初版实现逐字节做 `BigInt` 运算（`0xcbf29ce484222325n` 的 FNV-1a 64 位），每次迭代产生 BigInt 分配与装箱。

修复：改为**两路 32 位哈希**（FNV-1a 32 位 + 二次混合），全部使用 `Math.imul` 整数运算，输出 16 位十六进制指纹，保留「同输入同输出」的稳定性。

| 版本 | 2048×2048 单次耗时 | 1024×1024 单次耗时 |
| --- | ---: | ---: |
| 修复前（BigInt FNV-1a 64） | 2610 ms | 约 640 ms |
| 修复后（双路 32 位） | **61.8 ms** | **8.2 ms** |

约 **42×** 提速，且 `fixtures.test.ts` 中的稳定性与区分度断言全部通过。这是 P0 交付的第一个真实算法性能问题。

## 7. 对 P1/P2 设计的直接影响

1. **预览必须降分辨率**：1MP 单遍像素运算 10–40ms、4MP 47–176ms。交互预览应控制在 ≤512²（<10ms），高清结果延迟渲染，禁止每次鼠标移动全分辨率重算。
2. **禁止在交互路径做 PNG 编解码**：4MP 编码 127ms、解码 236ms；画布与位图之间应直接传递 `RasterImage`，编码只在导出/落盘时发生。
3. **结果指纹可用于缓存**：`hashRaster` 1MP 8.2ms 足够作为「相同输入 + 相同参数」的缓存键，配合参数指纹实现复用。
4. **内存纪律**：单张 4K RGBA 占 64MB，多副本会迅速逼近移动端上限；实现时必须原位写入或分块处理。
5. **接缝/颜色算子的成本上限**：颜色变体类算子接近 `noise`（4MP ≈ 176ms），属于必须走预览分级 + 异步的范畴。
