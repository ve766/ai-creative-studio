# ADR 0003：云端优先，零自建服务器

- 状态：已采纳
- 日期：2026-10-18

## 背景

原始任务书要求 Python + FastAPI 服务、PostgreSQL 主机、Redis、Celery 常驻工作进程，即需要长期运维服务器。实际约束是：开发者目标是「开发软件并通过托管平台上线」，不打算购买或维护服务器、GPU 或数据库主机。

## 决策

保留清晰的服务端业务边界，但将运行载体改为托管服务：

| 原始要求 | 采纳方案 |
| --- | --- |
| 自建 FastAPI 服务 | Next.js 应用内的 Route Handlers（`/api/v1`），部署到托管 Web 平台 |
| 自建 PostgreSQL 主机 | 托管 PostgreSQL（含行级安全），迁移脚本版本化 |
| Redis + Celery 常驻工作进程 | 托管任务/工作流服务，前端通过任务 ID 轮询状态 |
| 自建对象存储 | S3 兼容托管对象存储（预签名客户端直传） |
| 自建监控 | 托管错误监控 + 平台日志 |

Docker 仅用于本地开发与测试（可选的本地 PostgreSQL），**不是正式运行的必要条件**。

## 理由

- 消除运维面：无 Linux、Nginx、GPU 驱动、Kubernetes
- 成本可控：按需计费 + 免费额度起步，避免长期固定成本
- 与 Next.js 技术栈一致，减少一套语言与框架的维护成本

## 后果

- 必须检查托管平台的限制：单次请求时长、请求体大小、函数内存、数据库连接数、免费与付费差异
- 所有耗时任务必须异步化（任务 ID + 状态查询），不得依赖 Web 请求长期运行
- 外部服务必须通过 Provider 接口接入，避免供应商锁定（见 `docs/cloud-architecture.md`）
- 正式部署、付费开通、生产数据库迁移必须获得明确授权

## 备选方案

- 按原任务书自建：违背「零自建服务器」约束，已否决
- 全部逻辑放前端、完全没有服务端：无法安全地保存密钥、校验权限与额度，已否决
